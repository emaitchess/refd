# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is the tool-neutral twin of this file — apply any change to both.

## What this is

refd (refd.ai) — open-source AI search monitoring. Each workspace tracks one brand's visibility, mentions, citations, and rank across AI answer surfaces: ChatGPT, Perplexity, Gemini, Google AI Mode (BrightData dataset scrapers), and Google AI Overviews (BrightData SERP API). BrightData is the **only** data provider. Available hosted (refd.ai) or self-hosted; born tracking mrmr, since generalized. Public copy never pairs "refd" with "aeo".

Reference docs: `DESIGN.md` (design system — all UI work follows it), `docs/METRICS.md` (scoring and aggregation contract), and `docs/mcp.md` (remote MCP and OAuth usage).

## Monorepo layout

Bun workspaces (`apps/*`, `packages/*`) — three independently deployed Cloudflare Workers plus a shared package (`docs/plan-three-worker.md`).

- **`apps/api`** (`@refd/api`, `api.refd.ai`) — the Worker: Hono API, OAuth, MCP, cron trigger, queue consumer, every binding (D1, R2, KV, Queues, AI, Browser, rate limits), and secrets (`apps/api/.dev.vars` locally). **The only Worker that declares bindings, cron, or queue consumers** — CI enforces this via `scripts/check-worker-topology.sh`.
- **`apps/dashboard`** (`@refd/dashboard`, `dash.refd.ai`) — the React + Vite SPA as an **assets-only** Worker (`@/*` → `src/*`). `noindex`, with its own `public/robots.txt` + `public/_headers` (CSP allows `api.refd.ai`) and no landing route. It calls the API cross-origin, so its client builds absolute URLs from `VITE_API_ORIGIN` and sends `credentials: 'include'`.
- **`apps/web`** (`@refd/web`, `refd.ai`) — the public site: a static **Astro** build fronted by a tiny Worker (`src/worker.ts`) that does homepage Markdown negotiation over the assets. Owns the indexable SEO assets (`apps/web/public/`), the sitemap and llms.txt routes, JSON-LD, and the static 404. Pure `.astro` (Biome-excluded; `astro check` can't run on the repo's TS 7, so `astro build` validates the templates); CTAs link to `dash.refd.ai`.
- **`packages/core`** (`@refd/core`) — runtime-neutral code shared across Workers (`config`, `surfaces`, `mentions`, `workspaces`, `site-metadata`, `blocks`, `metric-copy`, `glossary`, `concepts`, `public-pages`), imported via subpaths like `@refd/core/config`. No build step; consumers bundle the TS source.

Root commands orchestrate all three Workers (Bun only, no extra task runner): `check` fans out `tsc`/`wrangler types` per workspace, `build` builds each, `deploy` builds (baking `VITE_API_ORIGIN=https://api.refd.ai` into the dashboard) then, after `db:migrate:remote`, deploys all three. Per-workspace scripts run via `bun run --filter '@refd/<name>' <script>`; Drizzle migrations + `drizzle.config.ts` stay at the repo root. **Cutover** (owner-run) needs `api.`/`dash.` custom domains and a fresh `OAUTH_KV` namespace — there is no backward-compat layer.


## Code style

- Add a code comment **only when it is absolutely necessary** to explain something non-obvious — a constraint, an invariant, a why (e.g. why the deep-walk extractor exists, why a snapshot is per-sample). Unnecessary comments are noise: never narrate what the next line does, restate a name, or pad with boilerplate. When in doubt, leave it out.
- Arrow-function definitions everywhere (`const f = () => {}`), never `function` declarations — including the vendored dither-kit sources (converted via codemod; still `@ts-nocheck` and excluded from Biome). Only the generated `worker-configuration.d.ts` keeps `declare function`.
- **Validate data at trust boundaries with Zod (`safeParse`), never bare `as` casts.** Applies to request bodies (`parseBody`), LLM output (`parseJson(raw, schema)` in `lib/llm.ts`), external API responses (BrightData envelopes, Exa, Browser Rendering), and queue-message intake. For untrusted LLM/external output prefer *lenient* schemas — truncate over-long strings via `.transform`, `.catch()` non-critical fields, require only what's essential — so one bad field never discards an otherwise usable result. The one deliberate exception is the scraped provider **record payloads**, which stay schema-agnostic for the deep-walk extractor (see Scoring).

## Commands

- `bun install` / `bun run <script>` / `bunx <tool>` — Bun is the package manager and script runner. Do not use npm/npx/node. Deployed runtime is workerd, so no Bun-specific APIs in `apps/api/src/`.
- Start every new feature or bug fix in a [wt](https://github.com/emaitchess/wt) worktree (`wt create <name>`), and manage worktrees with `wt` (`ls`/`open`/`rm`) — never raw `git worktree`. `wt create` runs the checked-in `.wt/setup.sh` (installs dependencies, copies local secrets and wrangler state), so a fresh worktree behaves like the main checkout while the main repo stays unblocked for parallel work.
- Wrangler invocations go through the `wrap` alias (wrangler with an isolated personal-account credential store; the API workspace's package scripts route through it). Use `wrap ...` or the repo scripts — never bare `wrangler`, which can pick up ambient work-account credentials.
- `bun run dev` runs all three Workers behind Caddy for real HTTPS on same-site subdomains: Astro at `refdlocal.io`, the dashboard Vite server at `dash.refdlocal.io` (`VITE_API_ORIGIN=https://api.refdlocal.io`), and the API `wrangler dev` at `api.refdlocal.io` (`DASHBOARD_ORIGIN`/`API_ORIGIN` in `apps/api/.dev.vars`). Add the three hosts to `/etc/hosts`; one-time `caddy trust`. Coordinated shutdown via a shell trap; this exercises real CORS, secure cross-subdomain cookies, OAuth redirects, and WebSocket streaming.

- `bun run check` (tsc) · `bun run lint` / `lint:fix` (Biome) · `bun test` (scoring unit tests) · `bun run build` · `bun run deploy`.
- **Merging to `main` is the release.** Cloudflare's Git integration builds and deploys all three Workers on every push to `main` (the API deploy applies remote D1 migrations first; the web deploy snapshots the sitemap and submits IndexNow). Never run `bun run deploy` against production and never ask the owner to deploy — a merged PR is a deployed PR. `bun run deploy` is the self-hosted/manual path.
- `bun run db:generate` (drizzle-kit after schema edits) · `db:migrate:local` / `db:migrate:remote` · `db:reset` (stop dev first — wipes `apps/api/.wrangler/state/v3` and re-applies migrations for a clean-slate onboarding test).
- No seed or user scripts exist. Users self-register on the login screen (email + password ≥ 8 chars, per-IP rate-limited; **business email only** — free-provider + disposable domains rejected); the first workspace is auto-created and the user lands in the resumable onboarding wizard. Data is isolated per workspace (owner-only). Entities and prompts are managed in the dashboard UI; passwords change in Settings (revokes other sessions).
- Secrets: `.dev.vars` locally, `wrangler secret` in prod (`JWT_SECRET`, `BRIGHTDATA_API_TOKEN`, `BRIGHTDATA_WEBHOOK_SECRET` for authenticated snapshot-ready callbacks, `ADMIN_EMAILS` as the comma-separated operator allowlist; `EXA_API_KEY` for onboarding competitor discovery via Exa company search — optional, the step soft-fails to manual entry without it. Exa is retrieval-only: candidate domains come from real indexed result URLs, and glm-5.3 curates by candidate number so it can never invent a domain (the Sonar failure that prompted the swap)). Never in code. Onboarding uses two **bindings, not secrets**: `AI` (Workers AI `@cf/zai-org/glm-5.3`, OpenAI-style `choices[].message.content`) and `BROWSER` (Browser Rendering Quick Actions: `markdown` drafts the brand description and `scrape` fetches homepage metadata for the report, cached in the workspace profile). Both are `remote: true` in apps/api/wrangler.jsonc so local dev proxies to the real service — `quickAction` isn't emulated locally, and both need Workers AI + Browser Rendering enabled on the account.
- Changing `database_id` in apps/api/wrangler.jsonc re-keys the local miniflare D1 file — re-run migrations and recreate local data after.

## Architecture (the big picture)

**Three Cloudflare Workers, one repo** — `refd-api` (`apps/api/src/`, `api.refd.ai`): Hono API, OAuth, MCP, cron, queue consumer, every binding. `refd-dashboard` (`apps/dashboard/`, `dash.refd.ai`): the React SPA as an assets-only Worker (noindex). `refd-web` (`apps/web/`, `refd.ai`): the static Astro public site with a tiny asset-fronting Worker for homepage Markdown negotiation. The dashboard calls the API cross-origin (see Monorepo layout and Auth).


- **Public indexing**: `public/robots.txt` and the IndexNow ownership key are static assets. `/sitemap.xml` is a **prerendered Astro route** (`apps/web/src/pages/sitemap.xml.ts` → `src/lib/sitemap.ts`) built from `INDEXABLE_PUBLIC_PATHS` in `packages/core/src/public-pages.ts` — there is no generator script and no checked-in XML. Whenever adding a canonical public page that search engines should index, add its path to `PUBLIC_PAGE_PATHS` and `INDEXABLE_PUBLIC_PATHS`. Never add sign-in, onboarding, authenticated, utility, redirect, or other non-indexable routes, and never add a `.md` twin (they are not canonical). The web deploy (`scripts/deploy-web.ts`) snapshots the live sitemap before publishing and submits newly added canonical paths to IndexNow automatically. After deploying changed existing pages, submit only those paths with `bun run --filter '@refd/web' indexnow -- /changed-path`. Reserve `--all` for initial setup or a real whole-site change.
- **The public site is agent-readable, and that is a contract**: every public page is also served as markdown at its own path with `.md` appended — `[...path].md.ts` covers content entries and glossary terms, and index/`.astro` pages have hand-written twins (`blog.md.ts`, `docs.md.ts`, `glossary.md.ts`, `demo.md.ts`, `trackers.md.ts`, `agents.md.ts`, `public/index.md`). `/llms.txt` follows the [llmstxt.org](https://llmstxt.org/) format (H1, blockquote, prose, H2 file lists of `- [name](url): notes`, `## Optional` last) and **every link in it points at the `.md` version**; its sections are derived from the `section` each entry carries in `apps/web/src/lib/public-content.ts`, so a new content entry files itself with no edit to `llms.txt.ts`. `/llms-full.txt` inlines the same documents, ordered by section, with each document's headings demoted one level so the file keeps one outline. A new `.astro` page therefore needs a hand-written `.md` twin plus `markdownPath` on `Base` (which emits `rel="alternate" type="text/markdown"`); `Base` emits `rel="describedby"` to `/llms.txt` site-wide. Data an `.astro` page and its `.md` twin both render belongs in a shared `src/lib/` module (see `agent-access.ts`), never duplicated.

Data flow:

```
cron (15m UTC tick) → for EACH eligible workspace DUE on its run schedule (workspaces.schedule, null = daily 06:00 UTC): run row (key cron:<wsId>:<date>) → Queues:
  brightdata_trigger ×4×samples×batches (chatgpt, perplexity, gemini, google_ai_mode)
    → one snapshot per (surface, sample, batch of PROMPT_BATCH_SIZE) → notify webhook → fetch
      (one 25m backstop poll, then 60s polling backing off to 5m past 30m; the give-up
       deadline is 3h from the trigger; unconfigured local/self-hosted keeps 60s polling)
  serp_aio_fetch ×prompts×samples (google_aio, sync SERP API)
  per result: raw gzipped → R2, scores → D1
recovery cron (every 5m) → resume due initial-dispatch plans without creating runs
```

- **Multi-workspace tenancy**: `workspaces` (owner user; standard users maximum 5, administrators unlimited, with finite limits atomically enforced by the create endpoint). `entities`, `prompts`, `runs` carry `workspace_id`; everything deeper inherits scope through them. Data routes live under `/w/:workspaceId/*` behind `requireWorkspace` (owner-only; foreign workspaces 404). Hosted cron includes only active `pilot` and `subscribed` workspaces (`monitoringTier` + optional `monitoringEndsAt`); `snapshot_only` is the default and receives no scheduled run. Self-hosters use `SCHEDULED_MONITORING_POLICY=all`. Each workspace carries a **run schedule** (`workspaces.schedule`, edited in Settings via `PATCH /settings/schedule`; null = the default daily 06:00 UTC): daily, or weekly on chosen weekdays every N weeks (1-8), at a 15-minute-granular UTC time. The 15-minute cron (`SCHEDULE_TICK_CRON` in `apps/api/src/index.ts`) fires a workspace when its occurrence time has passed that UTC day and no run exists for the date key, so a missed tick catches up the same day and a schedule can never produce two runs on one date; a disabled schedule pauses runs, and monitoring-tier eligibility still gates everything. Schedule due-math and the dashboard's next-run preview share `packages/core/src/schedule.ts` (fixed Monday anchor 2026-01-05 so every-N-weeks is deterministic). Run keys remain `cron:<wsId>:<date>`, and a failing workspace never blocks the others. Registration auto-creates the user's first workspace; switching (sidebar, command palette, Settings) lands on the workspace-scoped parent page first — resource ids in the URL cannot survive a switch (`switchDestination`/`useSwitchWorkspace` in `apps/dashboard/src/lib/nav.ts`) — then remounts the dashboard on switch. `GET /config` is the authenticated client source of truth for account/workspace limits: standard users get 5 workspaces, 25 active prompts per workspace, and 3 enabled surfaces per workspace; emails in `ADMIN_EMAILS` get unlimited workspaces/active prompts and all available surfaces. The mutation endpoints and `createRun` enforce the same policy server-side, and retired prompts preserve history without consuming an active slot. A workspace isn't usable until it finishes the **resumable onboarding wizard** (`workspaces.onboardingCompleted` gates the dashboard via `RequireOnboarded`; step + editable drafts live in the nullable `workspaces.profile` JSON, served/mutated by the workspace-scoped `/onboarding` router — `brand`/`extract`/`competitors`/`prompts`/`PATCH`/`commit`, the AI steps soft-failing to manual). Each AI step drafts once on entry for free; a manual **regenerate is capped at one per step** (`profile.regen` counts server-side so a reload can't reset it, and only a *successful* draft counts) — over the cap the endpoint 429s and the UI toasts instead of calling. `needsSetup: true` (200) is the no-brand response on overview/prompts/sources.
- **Remote MCP**: `/mcp` is a stateless Streamable HTTP server behind `@cloudflare/workers-oauth-provider` (`/oauth/authorize|token|register` plus well-known discovery; Client ID Metadata Documents are enabled and require the `global_fetch_strictly_public` compat flag). Each OAuth grant carries validated `{ userId, scopes, connectionId, callbackTarget }` plus the workspace entitlement: a checked set (`workspaceIds`) or `allWorkspaces` (resolved at request time, so workspaces created after approval join with no re-approval), in any scope; only PATs stay single-workspace. Every tool resolves the workspace solely from those encrypted props and confirms active `mcp_connections` mirror rows (one per grant × workspace), never from tool args; every tool, read and setup alike, accepts an optional `workspace` id selector validated against the principal's granted set (`resolveGrantedWorkspace`), and a consent-time checkbox group plus an **Allow all** switch in `oauth/consent.ts` picks the entitlement in every mode (write mode adds an exclusive create-workspace row whose approval provisions a single-workspace grant). Two scopes exist: `data:read` (the twelve analytics tools) and `data:write` (the twelve setup tools and `revoke_connection`: `create_workspace` is gated to Allow-all grants, the only entitlements that resolve workspaces created after approval, `complete_setup` wraps `POST /onboarding/complete`, `check_domain` resolves a domain and its redirect chain so candidate domains are verified before they are saved, and `revoke_connection` is self-limiting destruction - it revokes only the grant the credential itself resolves to, after an explicit `confirm` argument, sharing the revocation path Settings uses). Eleven operational tools in `mcp/ops-tools.ts` (`list/add/update/toggle/remove_prompt`, `run_now`, `add/remove/list_competitors`, `enable/disable_surface`) manage onboarded workspaces row by row, sharing the `lib/prompt-store.ts` + `lib/entity-store.ts` atomic helpers the dashboard prompts and entities routes use (create/update/bounded-activate/retire-or-delete, all honoring the active-prompt ceiling); they refuse workspaces whose setup has neither committed nor completed, and `run_now` reuses `createManualRun` (`ingest/runs.ts`, the operator HTTP route's same path) gated to `ADMIN_EMAILS` with the 5/hour manual-run guard; consent provisions a workspace inside the CSRF-protected approval POST (idempotent `workspaces.provisioning_key`, same atomic entitlement guard as `POST /workspaces`), access tokens carry only the scopes requested at exchange time, and `resolveMcpPrincipal` verifies token scopes are a subset of the live connection. Setup mutations ride the shared `onboarding/` services with CAS draft versions (`workspaces.onboarding_draft_version`) and durable `setup_usage` budgets; `confirm_setup` verifies the server-recomputed canonical hash, claims the one free report, and writes an immutable `setup_commits` row pinning the run group. `void-unspent` operator recovery fails closed unless zero provider acceptance is provable. Client identity is always self-reported, so consent labels the app unverified and shows the normalized callback target (HTTPS or loopback/native scheme only — remote plain-HTTP is rejected at registration and consent; helpers in `oauth/security.ts`), persisted to `mcp_connections.callbackTarget` and surfaced in Settings. The twelve analytics tools and metric-glossary resource are read-only and reuse dashboard metric/digest accessors. Native bindings rate-limit OAuth per IP and MCP per token fingerprint. Settings lists and revokes workspace connections; workspace/account deletion revokes provider grants before data cleanup. Headless clients (CI, cron, sandboxed agents) authenticate with workspace-scoped read-only personal access tokens (`refd_...`; only a SHA-256 hash is stored, the token is shown once, ≤10 active per workspace, revoked in Settings → Personal access tokens): the provider's `resolveExternalToken` turns a valid token into grant-shaped props carrying `tokenKind: 'pat'`, and principal resolution confirms the `api_tokens` mirror row instead of `mcp_connections`. See `docs/mcp.md`.
- **D1 (Drizzle, `apps/api/src/db/schema.ts`)**: users, workspaces, entities, prompts, runs, snapshots, results, entity_scores, citations, login_attempts, mcp_connections, api_tokens, setup_usage, setup_commits, chats, chat_messages. Unique keys are the idempotency backbone: results on `(runId, promptId, surface, sample)`, snapshots on `(runId, provider, surface, sample, chunk)`, runs on `key`. New runs persist an immutable, versioned initial-dispatch plan plus a CAS lease, cursor, bounded attempts, and backoff; the five-minute recovery cron and the account-wide operator route resume the same run, while pre-migration rows remain explicitly `legacy`. Queue delivery is at-least-once and BrightData has no idempotency key: a crash after provider acceptance but before snapshot/result persistence can replay a paid call, so uniqueness guarantees convergent stored data, not exactly-once provider spend. Messages carry the run's frozen prompt set so mid-run prompt edits can't skew a run.
- **Snapshots are per (surface, sample, chunk)** — prompts fan out to BrightData in batches of `PROMPT_BATCH_SIZE` (default 5), one snapshot per batch, so a dropped download fails one batch rather than the whole surface (`snapshots.promptIds` and `promptSnapshot` freeze the batch for retries/webhook fetches). Samples never share a snapshot: identical prompts in one batch risk being collapsed, which would silently break sampling. With `PUBLIC_BASE_URL` + `BRIGHTDATA_WEBHOOK_SECRET`, BrightData pushes the scraped records themselves to `POST /webhooks/brightdata` (the `endpoint` trigger param delivers data, not a status note); the handler stashes the raw delivery in R2 and enqueues a `brightdata_delivered` message, and one 25-minute backstop poll is insurance for a missed callback. Without both values, the existing 60-second polling loop remains active. A batch that is still `running` at the provider is given until `SNAPSHOT_DEADLINE_MS` (3h) **measured from `snapshots.createdAt`**, not from a poll counter: the old 60-poll budget was counted from the first backstop poll, so it silently expired ~90 minutes after the trigger and wrote off batches the provider was still working on (2026-09-27: two of twelve `google_ai_mode` batches were running at 91 minutes, one ready on the final permitted poll). The deadline is the single give-up rule and it is restart-safe because it reads a stored column. The poll interval backs off 60s to 5m past `SNAPSHOT_HEALTHY_MS` (30m, also the threshold `GET /runs/:id` reports a batch as `slow`) so a long wait does not enqueue ~180 messages per batch. A terminal failure is logged. A run finishes on **coverage** (`results` rows reach `totalCount`), not on success, so a surface that loses batches used to end the run quietly short; `runProgress` (`ingest/progress.ts`) is what `GET /runs/:id` returns to make the shortfall legible (per-surface stored/expected/ok/failed, in-flight batches with their wait, and a `slow` flag), and the run page renders it.
- **R2**: raw payloads, always gzipped (`CompressionStream`), deterministic keys `raw/{runId}/{promptId}-{surface}-{sample}.json.gz`, served back **decompressed** (`DecompressionStream`) — returning the stored bytes with `Content-Encoding: gzip` does not work: the runtime strips that header from an automatic-encoding response but leaves the body compressed, so the client renders gzip as text.
- **Scoring (`apps/api/src/scoring.ts`)** is provider-agnostic over `NormalizedAnswer { answerText, citationUrls, answerPresent, raw }`. The deep-walk extractor is intentional: provider schemas drift, and a walk degrades to "missed nothing" rather than silently missing everything. Position = order of first mention among tracked entities. The dataset normalizer post-filters walked source URLs (`dropRootArtifacts`/`isIconAsset` in `providers/brightdata.ts`): a bare site-root duplicating a deeper same-origin URL (Perplexity/AI Mode put a full URL in citation `domain` fields) and favicon/thumbnail service assets (gstatic, Google favicon service, from citation `icon` fields) never become citations, and a trailing ChatGPT sponsored unit is cut from the scored text (`stripSponsoredTail` — an advertiser is not an organic mention; the cut is double-anchored and warns instead of trimming when the shape drifts). Scores are versioned (`SCORING_VERSION`, stamped per `entity_scores` row; 0 = pre-versioned legacy) and rescorable from the R2 raws with zero provider spend: `POST /runs/:id/rescore` replays one run inline, `POST /runs/rescore` starts a queue-chained workspace backfill (`rescore_batch` messages in `apps/api/src/ingest/rescore.ts` + `consumer.ts` — cursor batches, idempotent, per-result failures stay stale rather than wedging the chain). Operator levers only; the backfill's UI is a dev-build-only Settings card. **Sentiment** (`entity_scores.sentiment`) is post-scoring enrichment, deliberately outside the deterministic scoring path: storing a scored answer with mentions enqueues one `sentiment_score` message, and the consumer classifies every mentioned entity in a single call (`classifySentiments` in `lib/llm.ts` — entities referenced by number so the model can't introduce one, grounded with the matched span text when an alias matched; malformed output leaves null, never a guess). Null = unclassified ("—"), aggregates count classified mentions only; a rescore carries labels over, and both the per-run rescore endpoint and the queue backfill re-drive classification for results whose mentioned rows are still unclassified (the handler no-ops on fully labeled results). Output is bounded by a response_format json_schema (default classifier glm-5.3-flash, eval-backed; `SENTIMENT_MODEL` overrides); entities whose first mention lies beyond the capped prompt window get a second tail-window pass, `rescoreProgress` reports the pending-coverage backlog, and misses are logged rather than guessed. Unparseable model output retries via the queue rather than acking nulls.
- **Home chat ("talk to the data")**: `/w/:id/chat` (`routes/chat.ts` + `routes/digest.ts`, `chat/exchange.ts` + `chat/exchange-do.ts`, `pages/Home.tsx`) is the post-login landing page. Grounding contract: the server builds a keyed digest (last 30 days, same pure metric functions as the dashboard); it is recomputed per question, so a rescore corrects what future answers see. The exchange runs in a **ChatExchange durable object** — one instance per chat (`idFromName(chatId)`, SQLite-backed via `new_sqlite_classes`), a coordinator over D1, never a store: `chats`/`chat_messages` stay in D1, which keeps the 30-messages-per-hour rate limit workspace-wide and lets workspace deletion clean chats up through foreign keys. `POST /chat` and `POST /chat/:id/messages` validate, rate-limit, and start the exchange, returning before the model runs; `GET /chat/:id/exchange` proxies a **hibernatable WebSocket** to the object, which replays everything so far (steps, prose so far, or the terminal done/error) then streams live events with the same shapes the old SSE frames used, so the dashboard change was transport-only. The engine (`chat/exchange.ts`) separates planning from answering: **glm-5.3** (`LLM_MODEL` in `lib/llm.ts`) streams plain markdown prose, and a separate structured-output call on **glm-5.3-flash** (`PLANNING_MODEL`) extracts title/links/proposal/webSources against a `response_format` json_schema, so protocol output can never leak into the prose (the `@@META@@` trailer is gone). The panels are picked by a second flash call (`extractPanels`) that starts with the digest, before gathering — it reads the question and the digest, not the answer, so its latency is absorbed by the tool loop — and its result is emitted as a `meta` stream event gated on the first streamed token (the text always leads, panels land as support for it), replayed from object storage like steps and prose, and the picked panels become the stored message's `panels`/`panelData`. Gathering is **native tool calling** on the flash model: tools are declared once in `routes/tool-registry.ts` (Zod schema generates the JSON Schema contract the model reads, so the contract and the validation cannot drift, plus a weighted cost) and dispatched by `routes/agent-tools.ts`: `list_prompts`, `get_digest`, `get_prompt_results` (JS matching, never SQL LIKE — D1 caps pattern length), `query_results` (one-call filtered answer table), `aggregate` (grouped metrics through the digest's own pure functions), `get_changes` (deterministic run comparison through the changes engine), `read_answer`, `read_mentions` (excerpts around stored mention spans), `get_citations`, `fetch_url` (renders a cited page to markdown via Browser Rendering — the citation allowlist is the security boundary: the URL must already exist in this workspace's citations, http(s) only, truncated and wrapped in an explicit untrusted marker), and `search_web` via Exa when `EXA_API_KEY` is set. Gathering runs under a weighted budget (`TOOL_BUDGET` = 30, costs 1-5) with a 20-round guard; identical-argument repeats are skipped with a trace line, near-duplicates that only vary the date window are capped at two, and `runChatWithTools` logs per-call `cached_tokens` so context caching is measurable. `panels` are digest-section keys the client renders as real components from `panelData` **frozen onto the message** (old conversations keep the numbers they showed, not today's); `links` survive only when they match the internal-path whitelist; `step` events carry the honest work trace (digest read with real counts, model call, panel selection), persisted per message with the exchange duration. Writes exist only as **proposals** (`chat_messages.proposal` + cited `sources`), applied/dismissed once via `POST /chat/:id/messages/:mid/proposal`, which re-validates through the same sanitizers/dedupe as the prompts/entities routes — the model never writes to tables, so web prompt-injection can at worst produce a suggestion a human reviews. A 5-minute alarm stops a wedged exchange, and terminal state is retained in the object until the next exchange on that chat starts, so a client connecting after the end still learns the outcome instead of hanging. Chats persist in D1 (workspace deletion cleans them up); 30 messages/hour per workspace. **Suggestion chips** are ranked, not gated (`routes/suggestions.ts`): each family (contested prompt, change event, named/unnamed split, weak surface, zero-visibility cluster, source gap, collection shortfall) declares the bar at which it becomes worth saying, and `strength` is how far past its own bar the observation landed — so families with incomparable raw units rank together and a candidate under its bar is dropped rather than shown. Every chip states a number and names a thing; `label` is what the chip shows and `question` is the fuller fact sent to the agent. At most two chips per family, and the canned starters only fill slots measurement left empty. The digest carries `contested`, `contestedCount` and `namedSplit` for this and for the agent's own grounding — the aggregate mention rate can be carried almost entirely by prompts that spell out the brand, so the split is stated rather than left to be inferred. The digest is recomputed per question, so a rescore corrects what future answers see.
- **Change alerts (`apps/api/src/routes/changes.ts`)**: derived on read, never stored — `GET /w/:id/changes` compares the two most recent *completed* runs with the same pure metric functions and emits thresholded events (5pp mention/citation rate, 4pp SOV, 5pp sentiment shares, a quarter of a rank of position; ≥4 shared cells, ≥3 positioned/classified mentions for position/sentiment; capped at 6, severity-sorted). Honesty guards: only the runs' shared (prompt × surface) cells compare, so a subset run can never fabricate a change; set-relative events (SOV/position/competitor, rises only for competitors) are suppressed when `entitySetHash` differs or is null; per-surface events fire only when the overall delta stayed quiet. One engine, two surfaces: the Overview "What changed" card and the Home idle chips (top two events as prefilled agent questions; the card's "ask" deep-links `/home?ask=`, prefill only, never auto-send). Surface display names for server-composed copy live in `packages/core/src/surfaces.ts` (the client re-exports them from `lib/format.ts`). Thresholds are restated in the glossary entry "Material change" and pinned to the engine constants by `changes.test.ts`.
- **Auth is self-built**: email+password (bcrypt via `bcryptjs`, cost 12 — workerd forbids runtime WASM so argon2/pbkdf2-wasm libs throw, and it caps native WebCrypto PBKDF2 at 100k iterations; bcrypt is pure-JS and embeds cost+salt so the work factor is upgradeable), HS256 JWT via `jose` (algorithm-pinned) in httpOnly SameSite=Strict cookie, 7d sliding renewal, `tokenVersion` revocation, login rate-limited via D1. No Cloudflare Access. Only `/auth/login`, `/auth/register`, and `/health` are unauthenticated. Register is gated to business emails (`apps/api/src/lib/email-policy.ts` — free-provider set + the `disposable-email-domains` list, loaded lazily). In the split deployment the session cookie stays host-only to `api.refd.ai` and `SameSite=Strict` still rides same-site subdomain requests from `dash.refd.ai`; the API grants credentialed CORS only to `DASHBOARD_ORIGIN` (`apps/api/src/lib/cors.ts`), answers the JSON preflight, and rejects session-authenticated mutations whose `Origin` is neither same-origin nor the dashboard. Webhooks, OAuth protocol calls, and bearer MCP are exempt.


- **Chat scope and evidence**: Each exchange resolves one exact UTC `ChatScope` from the accepted question timestamp (`resolveChatScope` in `lib/range.ts`): inclusive run-date bounds with calendar semantics, plus inheritance from the previous assistant message when a follow-up contains no new date words. The five date-scoped tools (`get_digest`, `get_prompt_results`, `query_results`, `aggregate`, `get_citations`) inherit that scope, and `applyToolScope` rejects broader model-supplied bounds. Every executed lookup lands in the server-owned evidence registry (`chat/evidence.ts`): `E0` is the initial digest and `E1..` follow tool execution order, with validated arguments, outcome, provenance, and scope. Live and persisted panels are bound to their selected evidence owner, cited web sources derive from prose `(S#)` markers, panels render only from evidence whose scope matches the question's exact window, an answer's markers are stripped of any id its own receipt cannot resolve, and `chat_messages.evidence` plus `selected_evidence_ids` preserve the receipt shown to the user.
- **Chat and raw-data durability**: `chat_exchanges` is the D1 source of truth for accepted, running, and terminal turns. Start requests carry a client UUID and atomically persist the exchange plus question before dispatch; duplicate requests resolve to the same HTTP 202 receipt. The Durable Object claims that exchange, persists monotonic sequenced events, and exact-exchange WebSockets reconnect with an `after` cursor. The assistant row and terminal verdict commit in one D1 batch, so cancellation, timeout, and stale model completion race through one CAS winner; a failed or timed-out exchange persists the evidence receipt of the lookups that ran before the stop, and gathering yields at a soft deadline so the alarm lands on an answer rather than a traceback; the object restores replay state from that D1 verdict after interruption. Conversation deletion leaves a permanent per-chat object tombstone. Workspace/account deletion first sets `workspaces.deleting_at` (and `users.deleting_at` for an account); authentication, provisioning, exchange acceptance, run dispatch, provider consumers, and raw-result storage honor those fences. Raw R2 prefixes are purged before their D1 ownership graph. `raw_cleanup_tasks` gives every raw write or cleanup a tokenized lease until its D1 result commits; cron claims expired leases and removes stale unreferenced objects, so compensation survives queue exhaustion and account deletion without stale work deleting a newer write.

## Domain rules that aren't obvious from code

- AI answers are non-deterministic. Hosted scheduled runs use `SAMPLES=1` to control collection cost; compare trends across completed runs, never one sample. The operator-only manual endpoint can request additional samples for a focused experiment.
- A missing Google AI Overview is a **valid result** (`answerPresent=false`), not a failure — AIOs appear on only ~15–20% of queries.
- "Mentioned" (named in answer text) and "cited" (domain in source URLs) are independent signals.
- **A brand metric is a statement about a set of prompts, so it names the set.** A prompt that spells out the brand is scored near 1.0 by construction, so the default blended aggregate flatters the brand (on the reference workspace, two brand-named prompts are 8% of answers and about half of all citations). `prompts.kind` (`discovery | alternative | brand_defining | market_perception | problem`, nullable = unclassified) is the cohort. `brand_defining` and `alternative` are **derived by the same matcher the scorer runs** over the prompt text against the tracked entity set, brand-named taking precedence; `discovery` is the derived floor for a prompt naming no tracked entity; `problem` and `market_perception` are **declared, never guessed**, because separating a problem-shaped question from a broad discovery one is a judgement about buyer intent that no substring settles (the same rule the rest of setup follows: ambiguity resolved at setup, never in a read); a NULL is resolved on the first cohort-aware read and never overwritten, so an explicit `update_prompt` kind survives. Every prompt-aggregating read (`get_visibility_overview`, `get_competitor_landscape`, `get_prompt_performance`, `get_digest`, `/overview`) takes a `kind` filter, and **an absent filter resolves to the discovery cohort rather than the blend** so a caller who asks nothing is never handed a brand-inflated number (`defaultHeadlineKind`, falling back to all cohorts only when a workspace has no discovery prompts, and naming that fallback in `population`). `get_visibility_overview` returns `headline` (which names its population) beside `byCohort` for all five cohorts and a `blended` block marked `deprecated: true` — kept for comparison, no longer at the top level so nothing reads it by accident. The filter is pushed into `loadScoreRows`, so a cohort rate is computed over cohort cells and is not a share of the blended rate. Cohort is independent of `category` (whose `Discovery` member is a buyer-journey stage, not the absence of a tracked name), which is why `tags` could not carry it. Contract: `docs/METRICS.md` "Prompt cohorts".
- **An attribute is the level a set is read at, and a single prompt does not measure it.** `prompts.attributeId` groups many differently-worded prompts under one capability (Profound's Topic, AppearIn's cluster, Scrunch's topic), because swapping a single label swings visibility 25-50 points, so a set with one prompt per attribute answers a question about phrasing rather than about the capability. Attributes are addressed by **label** and created on first use. `get_attribute_performance` reports per attribute the tracked prompt count, the count inside the reported population, active variants, the rates, and an **`unmeasured` flag when a single variant carries it**: an attribute with one prompt is untested, not scoring whatever that phrasing scored, and the floor for an attribute is two differently-worded prompts. Ungrouped prompts still run and are counted, and the rollup states how many. Contract: `docs/METRICS.md` "Attributes".
- **An intent axis is declared, never derived.** `prompts.funnelStage` (awareness | consideration | decision) and `prompts.questionType` (informational | navigational | commercial | transactional) are the industry-standard axes beside cohort, and both are **set by a human, never guessed from the text** for the same reason `problem` and `market_perception` are: no substring settles where a buyer is in a journey, and a guessed value is indistinguishable from a chosen one once it is a column. NULL means undeclared and never a default, so `get_intent_performance` counts an undeclared bucket rather than assuming awareness. **The two axes have no default filter, unlike cohort**: cohort defaults to discovery because a brand-named prompt inflates by construction, while blending stages neither flatters nor penalises, so an omitted axis filter means every declared value and the response names that population separately from the cohort. The axes are independent and an empty bucket sorts after the measured ones. Contract: `docs/METRICS.md` "Intent axes: declared, never derived".
- **A surface is never silently present or absent.** A surface switched off still has results inside a 30-day window, so `get_workspace_info` (the configured set) and the analytics (derived from rows) used to disagree with no label on either. `resolveSurfaceRegistry` (`lib/surface-registry.ts`) answers once for both: the union of the configured set and anything carrying data in the window, ordered by `SURFACE_ORDER` so chart series and colours stay stable, each tagged `enabled` or `historical`, and **the status repeats on every per-surface figure** so a number and its provenance cannot be read apart. `historical` is a real period (the surface was running) rather than a defect, and an enabled surface with no data yet is still present, because absence of data is not absence of a surface. Contract: `docs/METRICS.md` "Surfaces: configured versus measured".
- **A bounded list states its bound.** `get_prompt_performance` with `summary: true` caps `zeroVisibility` at ten and returns `{ count, prompts, truncated }`, so a caller reading only the count is never misled by the cap; the default read still returns the whole list under a 200-entry ceiling. Contract: `docs/METRICS.md` "Bounded lists".
- **A conditional mean is named for its denominator.** `averagePositionWhenMentioned` (renamed from `averagePosition`) is the mean rank over answers where the brand is mentioned, and it ships with `positionedAnswers` so the two cannot be read apart. A surface where the brand is mentioned in 3% of answers can still post exactly 1.000, because it leads with the most prominent entity; under the old name that read as a position the brand holds across the surface, which is the opposite of the truth. No threshold suppression: a low mention rate with a good rank is worth knowing. Contract: `docs/METRICS.md` "Position, when the brand is mentioned".
- **A metric states what it is measured over, and so does every event derived from it.** `get_recent_changes` compares only the prompt x surface cells present in both windows, so a rate event is a comparison of the same questions even when the live prompt set has moved on, and every event carries `measuredOver: 'shared-cells'`. `populationMatches` was one flag being read as two questions about two different populations; it is now `comparedOverSharedCells` (what the numbers are over) beside `liveSetUnchanged` (whether the questions are still tracked), with `status: 'population-moved'` so a consumer keying on status cannot read a comparison made across a population change as a clean bill of health, and a `caveat` sentence so no client re-derives it. Set-relative events (SOV, position) stay withheld across an entity or prompt break. `activePromptCount` is null, never 0, when the count could not be established. Contract: `docs/METRICS.md` "Change alerts: what an event is measured over".
- **A paid trigger has a dry run.** `run_now` spends provider quota, so `run_now_preview` (and `POST /runs/preview`) plans the identical dispatch and reports the provider records, queue messages, any requested prompt ids that are inactive or unknown, and the remaining hourly budget **without dispatching or counting against the 5/hour guard**. The preview is asserted against the run it previews rather than against arithmetic, because a preview that drifts from the run is worse than none. An empty prompt set is a refusal, not a price of zero. Contract: `docs/mcp.md` "Available tools".
- **A missing sentiment reading says why it is missing.** `sentimentDist` returns null for four different situations, and an em dash read identically for "the brand was never mentioned" and "classification has not caught up", which are opposite findings: one is an absence to fix, the other a queue still draining. `sentimentReading` reports `measured | pending | not-mentioned | no-answers` plus `mentionedAnswers`/`classifiedAnswers`/`unclassifiedAnswers`, and rides beside the distribution on every read path and in the dashboard. A partly-drained queue also withholds the sentiment change event outright, because two positive of two classified reads as 100% and reporting that as a tone shift reports the queue's progress as a change in the brand. Contract: `docs/METRICS.md` "Sentiment".
- **A version table that starts mid-history is worse than an empty one.** `prompt_set_versions` is only written by runs created after the feature shipped, so a workspace with a month of history reported its newest population as "first recorded population for this workspace" while the endpoint's own note told the reader to compare within a version. `ensurePromptSetHistory` recovers the history on read by deriving each historical run's population from its frozen `dispatchPlan`, minting one version per distinct population oldest first, and pointing those runs at it; it is idempotent, keyed on the run's own plan, and per workspace. `promptSetTimeline` matches runs by **hash**, not only by `versionId`, because a pre-feature run carries the hash and a null id, and an id-only match put a version's first run after the version that already existed. `sequence` is the workspace's own order (`versionId` is a global row id, so the first version is routinely numbered above 1) and `historyComplete` states whether every measured population is represented. Contract: `docs/METRICS.md` "Prompt population versions: recovering history".
- **An argument shape is part of the contract, so the published schema is what gets tested.** A caller sending `kind` as an array was refused with "The tool arguments did not match the published schema", blaming a schema that never claimed to reject it, while every test read the Zod object rather than the JSON Schema a client validates against. `promptKindFilterSchema` now takes a comma-separated string or an array, and `server.test.ts` converts each registered tool's schema and asserts the published properties match the parsed ones. Contract: `docs/METRICS.md` "Surfaces: configured versus measured" for the registry; the schema rule is about the argument, not a surface.
- **Trend honesty needs the prompt population, not just the entity set.** `runs.entitySetHash` identifies entities only, so a prompt-membership change was invisible to `get_recent_changes` and a share moving with a change of questions read as a visibility event. A run's prompt population is now `promptSetHash`, derived on read from the frozen `dispatchPlan` (a stored column would be null for every pre-existing run and would read as a break it cannot prove), hashed with the same djb2 as `entitySetHash`; a null population is **unknown, not changed**, and `promptSetKnown` says which. `promptCount` is the compared population while `activePromptCount` is the live set, and `populationMatches` is true only when they agree, so the ambiguous single count that made a stale population look authoritative is gone. Set-relative events (SOV, position) are withheld across a prompt break exactly as across an entity break; `populationNote` states the case in one sentence and never calls an unprovable population a change. A population is **versioned** on first measurement (`prompt_set_versions`, keyed by the same `promptSetHash` so the version and the detected break cannot disagree): every run carries `promptSetVersionId`, two runs sharing one provably measured the same questions, and `get_prompt_set_timeline` answers "which prompts were live in week 32" with what changed between versions. A surface change does not mint a version, and a membership change with no run yet has none, because a version records what was measured rather than what was edited. Contract: `docs/METRICS.md` "Prompt population and trend honesty".
- Manual runs spend paid quota (75 records at the standard workspace ceiling and one-sample default) — the normal user UI has no trigger, and every operator mutation under `/runs` requires the authenticated email in `ADMIN_EMAILS`; manual creation is additionally rate-limited (5/hour per workspace). Cron cost multiplies per entitled workspace. BrightData free tiers are nearly saturated at current volume; more prompts/samples/surfaces has real cost.
- Grok/Copilot surfaces are config-only additions (new `dataset_id` + surface enum) — no new client code.
- Each workspace picks which AI surfaces to track (`workspaces.surfaces` JSON, null = the entitlement default); `createRun` fans out only to the effective enabled surfaces (a real cost lever). Standard users can enable 3; administrators can enable all 5. Set in the onboarding prompts step + Settings via the `/settings` router (`enabledSurfaces()` validates, orders, and bounds stored selections).
- Onboarding `commit` fires a preliminary `onboard` run (1 prompt/category, sample=1, key `onboard:<wsId>`) that the report step polls live, plus a background `onboard-bg:<wsId>` run for the remaining prompts; the full set joins scheduled runs only when the workspace has recurring monitoring access. **`commit` does not finish onboarding** — the live report is the last wizard step, so `onboardingCompleted` flips only in `POST /onboarding/complete` ("enter dashboard", wrapped by the MCP `complete_setup` tool). `profile.committed` marks the in-between so a reload on the report resumes there rather than dropping back to Review and committing (and re-spending) a second time. `createRun` takes optional `{ promptIds, samples }` for these subset runs. The report shows only single-run-meaningful charts (tiles + per-engine + you-vs-competitors + brand sentiment); trend charts need ≥2 runs. Because sentiment classification trails each answer by a queue hop, the report keeps polling two grace cycles after the runs complete.
- Onboarding setup spend is budgeted in the `setup_usage` ledger: generation attempts per section (max 3 failures/24h), 18 external setup calls per standard user/24h, one report per workspace, one report per user/24h, five lifetime, plus global daily circuit breakers (`SETUP_GENERATION_DAILY_LIMIT`, `SETUP_REPORT_DAILY_LIMIT`). Claims are settled before and after external work; admins skip only the user-level caps. The setup state reads (dashboard GET and MCP `get_setup_state`) attach the caller's effective limits and a 24h ledger snapshot; generation failures carry a detail cause plus a guidance line naming the free-retry rule, and competitor search failures carry the raw indexed candidate domains. `suggest_prompts` takes optional steering (`total` clamped to the prompt limit, `focus` free text); the AI-path per-category cap widens to the requested spread. The setup report is pinned to the `setup_commits` run group and served to both the dashboard (`/onboarding/report/:setupId`) and MCP (`get_setup_report`).
- The local DB's run `import:2026-07-14` is back-imported legacy Oxylabs data (provider `oxylabs-import`, no R2 raw); the import script itself has been removed.

## UI rules (see DESIGN.md for full detail)

- Charts are dither-kit only, vendored under `apps/dashboard/src/components/dither-kit/`. The kit is **not** charts-only: it also ships standalone non-chart items (`gradient` — dithered background washes, used on the landing footer; `avatar`) that install without the chart engine. Add them **by hand**, never via `bunx @dither-kit/cli add` — those items co-ship `palette.ts`/`lib.ts`, which the CLI would overwrite, reverting the arrow-function codemod. Fetch the registry JSON (`components.json` → `@dither-kit`), take only the new files, codemod, add the `@ts-nocheck` vendor header; the dir is Biome-excluded. `gradient`'s `from` takes a palette name or a hue (fixed 85% saturation), so **`grey` is its only achromatic option** — what a monochrome wash must use.
- **No shadcn/ui** — `components.json` + `cn()` exist solely for the dither-kit registry; build components by hand with Tailwind.
- Monochrome chrome; hue belongs to data. Entity series colors: fixed order `green(brand), purple, red, blue, orange, pink`, 7th+ grey (`apps/dashboard/src/lib/chart-colors.ts`) — validated for CVD; never cycle or reorder per-view.
- ≤4 series per trend chart with a legend; text wears text tokens, never series colors.
- Every user-facing metric addition, rename, definition change, or removal must also update the glossary rendered by `apps/dashboard/src/pages/Help.tsx`. Keep its source of truth in `packages/core/src/metric-copy.ts` complete, including the metric's stable ID, category, definition, and details, and update the glossary tests in the same change. The public `/glossary` merges three sources under one URL namespace (`glossary-index.ts`): `metric-copy.ts` metrics, `glossary.ts` product terms, and `concepts.ts` category vocabulary (AEO, GEO, llms.txt, and the like). Only the first two are read by the product and rendered in Help; concepts are public-site only and their pages must never claim to be generated from the software.
- Scraped AI answer content is untrusted: render as escaped text or via react-markdown with no raw-HTML passthrough (`.md-body`) — never `dangerouslySetInnerHTML`. Citation URLs are scheme-checked before reaching an `href` (http(s) only; anything else renders inert). Entity mentions are highlighted by `rehypeHighlightEntities` (`lib/highlight.ts`), which wraps matches at the **text-node level of the parsed AST** — never by regexing the markdown string, which would corrupt hrefs and code. It runs the same shared matcher the scorer runs (`packages/core/src/mentions.ts` — `composeAliases` + `findMentionSpans`) so a highlight appears iff that entity is scored "mentioned"; there is no separate client rule, and `highlight.test.ts` guards the adapter wiring against drifting from what the scorer composes.
- Keyboard: `g`-chords navigate, `shift+?` shortcuts dialog, `⌘+/` sidebar, `t` theme (`apps/dashboard/src/components/Shortcuts.tsx`); sidebar rows show hints on hover. In the onboarding wizard, `onEnterKey` on a field submits/advances (Shift+Enter still newlines; in an add-form it adds the item instead) and `useEnterAdvance`/`useEscapeBack` handle the unfocused case — Enter only fires when nothing holds focus (a focused button already fires its own), Escape yields to any open popover (`[aria-expanded="true"]`) and to the prompt draft form before leaving the step.
- The theme is one external store (`useSyncExternalStore` in `lib/theme.ts`), not per-caller `useState` — four components read it, and a duplicated copy silently desyncs the ones that didn't toggle.
- **No em dashes in UI copy.** Recast with a period, comma, colon, or parentheses to fit the sentence. The standalone `—` is still the "no data" glyph in tiles and table cells (`pct`/`position` return it); that's a placeholder, not prose.
- Transient notices go through `useToast()` (`ToastProvider` sits at the app root) — bottom-center, self-clearing; use it for a refused action, not for form validation (that's the inline error line).
- Tables use the shared utilities in `apps/dashboard/src/components/table/table.tsx`: sort (`useSort`, nulls last), pagination (`usePagination`), resizable columns (`useColumnWidths` + `ColGroup`/`ColResizer` — a drag trades width with the neighbour so the total never changes; give every column a `fraction` for a stable default instead of letting the browser measure content), and `rowActivation()` for clickable rows (a bare `onClick` on a `<tr>` is mouse-only). Prompt detail opens in the shared `PromptPane` → `ResultPane` side panes (`apps/dashboard/src/components/panes/`).
