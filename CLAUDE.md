# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is the tool-neutral twin of this file — apply any change to both.

## What this is

refd (refd.ai) — open-source AI search monitoring. Each workspace tracks one brand's visibility, mentions, citations, and rank across AI answer surfaces: ChatGPT, Perplexity, Gemini, Google AI Mode (BrightData dataset scrapers), and Google AI Overviews (BrightData SERP API). BrightData is the **only** data provider. Available hosted (refd.ai) or self-hosted; born tracking mrmr, since generalized. Public copy never pairs "refd" with "aeo".

Reference docs: `docs/plan.md` (original implementation plan — historical; predates workspaces and registration), `docs/DESIGN.md` (design system — all UI work follows it), `docs/plan-metrics-v2.md` (metrics v2 implementation plan — fully executed; the design lives in `docs/FEATURES.md` → "Metrics (v2)").

## Code style

- Add a code comment **only when it is absolutely necessary** to explain something non-obvious — a constraint, an invariant, a why (e.g. why the deep-walk extractor exists, why a snapshot is per-sample). Unnecessary comments are noise: never narrate what the next line does, restate a name, or pad with boilerplate. When in doubt, leave it out.
- Arrow-function definitions everywhere (`const f = () => {}`), never `function` declarations — including the vendored dither-kit sources (converted via codemod; still `@ts-nocheck` and excluded from Biome). Only the generated `worker-configuration.d.ts` keeps `declare function`.
- **Validate data at trust boundaries with Zod (`safeParse`), never bare `as` casts.** Applies to request bodies (`parseBody`), LLM output (`parseJson(raw, schema)` in `lib/llm.ts`), external API responses (BrightData envelopes, Exa, Browser Rendering), and queue-message intake. For untrusted LLM/external output prefer *lenient* schemas — truncate over-long strings via `.transform`, `.catch()` non-critical fields, require only what's essential — so one bad field never discards an otherwise usable result. The one deliberate exception is the scraped provider **record payloads**, which stay schema-agnostic for the deep-walk extractor (see Scoring).

## Commands

- `bun install` / `bun run <script>` / `bunx <tool>` — Bun is the package manager and script runner. Do not use npm/npx/node. Deployed runtime is workerd, so no Bun-specific APIs in `src/`.
- `bun run dev` — Vite dev server with workerd bindings (Cloudflare Vite plugin); local D1/R2/Queues via miniflare state in `.wrangler/`. Also starts Caddy fronting it at https://refdlocal.io (stops on exit via shell trap in the script; needs `127.0.0.1 refdlocal.io` in `/etc/hosts` and one-time `caddy trust`).
- `bun run check` (tsc) · `bun run lint` / `lint:fix` (Biome) · `bun test` (scoring unit tests) · `bun run build` · `bun run deploy`.
- `bun run db:generate` (drizzle-kit after schema edits) · `db:migrate:local` / `db:migrate:remote` · `db:reset` (stop dev first — wipes `.wrangler/state/v3` and re-applies migrations for a clean-slate onboarding test).
- No seed or user scripts exist. Users self-register on the login screen (email + password ≥ 8 chars, per-IP rate-limited; **business email only** — free-provider + disposable domains rejected); the first workspace is auto-created and the user lands in the resumable onboarding wizard. Data is isolated per workspace (owner-only). Entities and prompts are managed in the dashboard UI; passwords change in Settings (revokes other sessions).
- Secrets: `.dev.vars` locally, `wrangler secret` in prod (`JWT_SECRET`, `BRIGHTDATA_API_TOKEN`, `BRIGHTDATA_WEBHOOK_SECRET` for authenticated snapshot-ready callbacks, `ADMIN_EMAILS` as the comma-separated operator allowlist; `EXA_API_KEY` for onboarding competitor discovery via Exa company search — optional, the step soft-fails to manual entry without it. Exa is retrieval-only: candidate domains come from real indexed result URLs, and glm-5.2 curates by candidate number so it can never invent a domain (the Sonar failure that prompted the swap)). Never in code. Onboarding uses two **bindings, not secrets**: `AI` (Workers AI `@cf/zai-org/glm-5.2`, OpenAI-style `choices[].message.content`) and `BROWSER` (Browser Rendering Quick Actions: `markdown` drafts the brand description and `scrape` fetches homepage metadata for the report, cached in the workspace profile). Both are `remote: true` in wrangler.jsonc so local dev proxies to the real service — `quickAction` isn't emulated locally, and both need Workers AI + Browser Rendering enabled on the account.
- Changing `database_id` in wrangler.jsonc re-keys the local miniflare D1 file — re-run migrations and recreate local data after.

## Architecture (the big picture)

**One Cloudflare Worker does everything** — Hono API (`src/api/`), cron trigger, queue consumer, and the React SPA (`src/app/`) served via Workers Static Assets. One `wrangler.jsonc`, one deploy to refd.ai.

- **Public indexing**: `public/robots.txt` is a static asset. `public/sitemap.xml` is generated by `bun run sitemap` before each build from `INDEXABLE_PUBLIC_PATHS` in `src/shared/public-pages.ts`; never edit the generated XML by hand. Whenever adding a canonical public page that search engines should index, add its path to `PUBLIC_PAGE_PATHS` and `INDEXABLE_PUBLIC_PATHS`. Never add sign-in, onboarding, authenticated, utility, redirect, or other non-indexable routes.

Data flow:

```
cron (daily 06:00 UTC) → for EACH eligible workspace: run row (key cron:<wsId>:<date>) → Queues:
  brightdata_trigger ×4×samples×batches (chatgpt, perplexity, gemini, google_ai_mode)
    → one snapshot per (surface, sample, batch of PROMPT_BATCH_SIZE) → notify webhook → fetch
      (one 25m backstop poll; unconfigured local/self-hosted environments keep 60s polling)
  serp_aio_fetch ×prompts×samples (google_aio, sync SERP API)
  per result: raw gzipped → R2, scores → D1
```

- **Multi-workspace tenancy**: `workspaces` (owner user; standard users maximum 5, administrators unlimited, with finite limits atomically enforced by the create endpoint). `entities`, `prompts`, `runs` carry `workspace_id`; everything deeper inherits scope through them. Data routes live under `/api/w/:workspaceId/*` behind `requireWorkspace` (owner-only; foreign workspaces 404). Hosted cron includes only active `pilot` and `subscribed` workspaces (`monitoringTier` + optional `monitoringEndsAt`); `snapshot_only` is the default and receives no nightly run. Self-hosters use `SCHEDULED_MONITORING_POLICY=all`. Run keys remain `cron:<wsId>:<date>`, and a failing workspace never blocks the others. Registration auto-creates the user's first workspace; the sidebar switcher sets the client's URL prefix and remounts the dashboard on switch. `GET /api/config` is the authenticated client source of truth for account/workspace limits: standard users get 5 workspaces, 25 active prompts per workspace, and 3 enabled surfaces per workspace; emails in `ADMIN_EMAILS` get unlimited workspaces/active prompts and all available surfaces. The mutation endpoints and `createRun` enforce the same policy server-side, and retired prompts preserve history without consuming an active slot. A workspace isn't usable until it finishes the **resumable onboarding wizard** (`workspaces.onboardingCompleted` gates the dashboard via `RequireOnboarded`; step + editable drafts live in the nullable `workspaces.profile` JSON, served/mutated by the workspace-scoped `/onboarding` router — `brand`/`extract`/`competitors`/`prompts`/`PATCH`/`commit`, the AI steps soft-failing to manual). Each AI step drafts once on entry for free; a manual **regenerate is capped at one per step** (`profile.regen` counts server-side so a reload can't reset it, and only a *successful* draft counts) — over the cap the endpoint 429s and the UI toasts instead of calling. `needsSetup: true` (200) is the no-brand response on overview/prompts/sources.
- **Remote MCP**: `/api/mcp` is a stateless Streamable HTTP server behind `@cloudflare/workers-oauth-provider` (`/api/oauth/authorize|token|register` plus well-known discovery). Each OAuth grant carries a validated `{ userId, workspaceId, scopes, connectionId }`; every tool resolves the workspace solely from those encrypted props and confirms an active `mcp_connections` mirror row, never from tool args. The nine tools and metric-glossary resource are read-only and reuse dashboard metric/digest accessors. Native bindings rate-limit OAuth per IP and MCP per token fingerprint. Settings lists and revokes workspace connections; workspace/account deletion revokes provider grants before data cleanup. See `docs/mcp.md`.
- **D1 (Drizzle, `src/api/db/schema.ts`)**: users, workspaces, entities, prompts, runs, snapshots, results, entity_scores, citations, login_attempts. Unique keys are the idempotency backbone: results on `(runId, promptId, surface, sample)`, snapshots on `(runId, provider, surface, sample, chunk)`, runs on `key`. Redelivered queue messages check-then-skip — never re-spend a provider record. Messages carry the run's frozen prompt set so mid-run prompt edits can't skew a run.
- **Snapshots are per (surface, sample, chunk)** — prompts fan out to BrightData in batches of `PROMPT_BATCH_SIZE` (default 5), one snapshot per batch, so a dropped download fails one batch rather than the whole surface (`snapshots.promptIds` and `promptSnapshot` freeze the batch for retries/webhook fetches). Samples never share a snapshot: identical prompts in one batch risk being collapsed, which would silently break sampling. With `PUBLIC_BASE_URL` + `BRIGHTDATA_WEBHOOK_SECRET`, BrightData notifies `POST /api/webhooks/brightdata` and the queue fetches immediately; one 25-minute poll is insurance for a missed callback. Without both values, the existing 60-second polling loop remains active.
- **R2**: raw payloads, always gzipped (`CompressionStream`), deterministic keys `raw/{runId}/{promptId}-{surface}-{sample}.json.gz`, served back **decompressed** (`DecompressionStream`) — returning the stored bytes with `Content-Encoding: gzip` does not work: the runtime strips that header from an automatic-encoding response but leaves the body compressed, so the client renders gzip as text.
- **Scoring (`src/api/scoring.ts`)** is provider-agnostic over `NormalizedAnswer { answerText, citationUrls, answerPresent, raw }`. The deep-walk extractor is intentional: provider schemas drift, and a walk degrades to "missed nothing" rather than silently missing everything. Position = order of first mention among tracked entities. The dataset normalizer post-filters walked source URLs (`dropRootArtifacts`/`isIconAsset` in `providers/brightdata.ts`): a bare site-root duplicating a deeper same-origin URL (Perplexity/AI Mode put a full URL in citation `domain` fields) and favicon/thumbnail service assets (gstatic, Google favicon service, from citation `icon` fields) never become citations, and a trailing ChatGPT sponsored unit is cut from the scored text (`stripSponsoredTail` — an advertiser is not an organic mention; the cut is double-anchored and warns instead of trimming when the shape drifts). Scores are versioned (`SCORING_VERSION`, stamped per `entity_scores` row; 0 = pre-versioned legacy) and rescorable from the R2 raws with zero provider spend: `POST /runs/:id/rescore` replays one run inline, `POST /runs/rescore` starts a queue-chained workspace backfill (`rescore_batch` messages in `src/api/ingest/rescore.ts` + `consumer.ts` — cursor batches, idempotent, per-result failures stay stale rather than wedging the chain). Operator levers only; the backfill's UI is a dev-build-only Settings card. **Sentiment** (`entity_scores.sentiment`) is post-scoring enrichment, deliberately outside the deterministic scoring path: storing a scored answer with mentions enqueues one `sentiment_score` message, and the consumer classifies every mentioned entity in a single glm-5.2 call (`classifySentiments` in `lib/llm.ts` — entities referenced by number so the model can't introduce one; malformed output leaves null, never a guess). Null = unclassified ("—"), aggregates count classified mentions only; new answers only — a rescore carries labels over, and the per-run rescore endpoint re-drives classification solely for still-unclassified mentioned rows (the queue backfill never classifies). Unparseable model output retries via the queue rather than acking nulls.
- **Home chat ("talk to the data")**: `/api/w/:id/chat` (`routes/chat.ts` + `routes/digest.ts`, `pages/Home.tsx`) is the post-login landing page. Grounding contract: the server builds a keyed digest (last 30 days, same pure metric functions as the dashboard) and answers stream over SSE — glm-5.2 writes markdown prose (forwarded as `delta` events token by token) then a `@@META@@ {json}` trailer with title/panels/links that is cut server-side (a sentinel-length tail is held back so it can never leak mid-chunk) and parsed leniently. `panels` are digest-section keys the client renders as real components from `panelData` **frozen onto the message** (old conversations keep the numbers they showed, not today's); `links` survive only when they match the internal-path whitelist; `step` events carry the honest work trace (digest read with real counts, model call, panel selection), persisted per message with the exchange duration. The exchange is **agentic**: a JSON decision loop (`TOOL_CAP` = 10) runs read-only tools from `routes/agent-tools.ts` (`search_web` via Exa, `get_prompt_results` — JS matching, never SQL LIKE (D1 caps pattern length), `read_answer`, `get_digest`) with each call as a step; writes exist only as **proposals** (`chat_messages.proposal` + cited `sources`), applied/dismissed once via `POST /chat/:id/messages/:mid/proposal`, which re-validates through the same sanitizers/dedupe as the prompts/entities routes — the model never writes to tables, so web prompt-injection can at worst produce a suggestion a human reviews. Chats persist in D1 (`chats`/`chat_messages`; workspace deletion cleans them up); 30 messages/hour per workspace; suggestion chips are computed from workspace state, never canned. The digest is recomputed per question, so a rescore corrects what future answers see.
- **Change alerts (`src/api/routes/changes.ts`)**: derived on read, never stored — `GET /w/:id/changes` compares the two most recent *completed* runs with the same pure metric functions and emits thresholded events (15pp mention/citation rate, 10pp SOV, 20pp sentiment shares, 1 rank position; ≥4 shared cells, ≥3 positioned/classified mentions for position/sentiment; capped at 6, severity-sorted). Honesty guards: only the runs' shared (prompt × surface) cells compare, so a subset run can never fabricate a change; set-relative events (SOV/position/competitor, rises only for competitors) are suppressed when `entitySetHash` differs or is null; per-surface events fire only when the overall delta stayed quiet. One engine, two surfaces: the Overview "What changed" card and the Home idle chips (top two events as prefilled agent questions; the card's "ask" deep-links `/home?ask=`, prefill only, never auto-send). Surface display names for server-composed copy live in `src/shared/surfaces.ts` (the client re-exports them from `lib/format.ts`). Thresholds are restated in the glossary entry "Material change" and pinned to the engine constants by `changes.test.ts`.
- **Auth is self-built**: email+password (bcrypt via `bcryptjs`, cost 12 — workerd forbids runtime WASM so argon2/pbkdf2-wasm libs throw, and it caps native WebCrypto PBKDF2 at 100k iterations; bcrypt is pure-JS and embeds cost+salt so the work factor is upgradeable), HS256 JWT via `jose` (algorithm-pinned) in httpOnly SameSite=Strict cookie, 24h sliding renewal, `tokenVersion` revocation, login rate-limited via D1. No Cloudflare Access. Only `/api/auth/login`, `/api/auth/register`, and `/api/health` are unauthenticated. Register is gated to business emails (`src/api/lib/email-policy.ts` — free-provider set + the `disposable-email-domains` list, loaded lazily).

## Domain rules that aren't obvious from code

- AI answers are non-deterministic — `SAMPLES=2` exists for that. Compare trends across runs, never single samples.
- A missing Google AI Overview is a **valid result** (`answerPresent=false`), not a failure — AIOs appear on only ~15–20% of queries.
- "Mentioned" (named in answer text) and "cited" (domain in source URLs) are independent signals.
- Manual runs spend paid quota (~180 records) — the normal user UI has no trigger, and every operator mutation under `/runs` requires the authenticated email in `ADMIN_EMAILS`; manual creation is additionally rate-limited (5/hour per workspace). Cron cost multiplies per entitled workspace. BrightData free tiers are nearly saturated at current volume; more prompts/samples/surfaces has real cost.
- Grok/Copilot surfaces are config-only additions (new `dataset_id` + surface enum) — no new client code.
- Each workspace picks which AI surfaces to track (`workspaces.surfaces` JSON, null = the entitlement default); `createRun` fans out only to the effective enabled surfaces (a real cost lever). Standard users can enable 3; administrators can enable all 5. Set in the onboarding prompts step + Settings via the `/settings` router (`enabledSurfaces()` validates, orders, and bounds stored selections).
- Onboarding `commit` fires a preliminary `onboard` run (1 prompt/category, sample=1, key `onboard:<wsId>`) that the report step polls live, plus a background `onboard-bg:<wsId>` run for the remaining prompts; the full set joins the nightly cron only when the workspace has recurring monitoring access. **`commit` does not finish onboarding** — the live report is the last wizard step, so `onboardingCompleted` flips only in `POST /onboarding/complete` ("enter dashboard"). `profile.committed` marks the in-between so a reload on the report resumes there rather than dropping back to Review and committing (and re-spending) a second time. `createRun` takes optional `{ promptIds, samples }` for these subset runs. The report shows only single-run-meaningful charts (tiles + per-engine + you-vs-competitors + brand sentiment); trend charts need ≥2 runs. Because sentiment classification trails each answer by a queue hop, the report keeps polling two grace cycles after the runs complete.
- The local DB's run `import:2026-07-14` is back-imported legacy Oxylabs data (provider `oxylabs-import`, no R2 raw); the import script itself has been removed.

## UI rules (see docs/DESIGN.md for full detail)

- Charts are dither-kit only, vendored under `src/app/components/dither-kit/`. The kit is **not** charts-only: it also ships standalone non-chart items (`gradient` — dithered background washes, used on the landing footer; `avatar`) that install without the chart engine. Add them **by hand**, never via `bunx @dither-kit/cli add` — those items co-ship `palette.ts`/`lib.ts`, which the CLI would overwrite, reverting the arrow-function codemod. Fetch the registry JSON (`components.json` → `@dither-kit`), take only the new files, codemod, add the `@ts-nocheck` vendor header; the dir is Biome-excluded. `gradient`'s `from` takes a palette name or a hue (fixed 85% saturation), so **`grey` is its only achromatic option** — what a monochrome wash must use.
- **No shadcn/ui** — `components.json` + `cn()` exist solely for the dither-kit registry; build components by hand with Tailwind.
- Monochrome chrome; hue belongs to data. Entity series colors: fixed order `green(brand), purple, red, blue, orange, pink`, 7th+ grey (`src/app/lib/chart-colors.ts`) — validated for CVD; never cycle or reorder per-view.
- ≤4 series per trend chart with a legend; text wears text tokens, never series colors.
- Every user-facing metric addition, rename, definition change, or removal must also update the glossary rendered by `src/app/pages/Help.tsx`. Keep its source of truth in `src/app/lib/metric-copy.ts` complete, including the metric's stable ID, category, definition, and details, and update the glossary tests in the same change.
- Scraped AI answer content is untrusted: render as escaped text or via react-markdown with no raw-HTML passthrough (`.md-body`) — never `dangerouslySetInnerHTML`. Citation URLs are scheme-checked before reaching an `href` (http(s) only; anything else renders inert). Entity mentions are highlighted by `rehypeHighlightEntities` (`lib/highlight.ts`), which wraps matches at the **text-node level of the parsed AST** — never by regexing the markdown string, which would corrupt hrefs and code. It runs the same shared matcher the scorer runs (`src/shared/mentions.ts` — `composeAliases` + `findMentionSpans`) so a highlight appears iff that entity is scored "mentioned"; there is no separate client rule, and `highlight.test.ts` guards the adapter wiring against drifting from what the scorer composes.
- Keyboard: `g`-chords navigate, `shift+?` shortcuts dialog, `⌘+/` sidebar, `t` theme (`src/app/components/Shortcuts.tsx`); sidebar rows show hints on hover. In the onboarding wizard, `onEnterKey` on a field submits/advances (Shift+Enter still newlines; in an add-form it adds the item instead) and `useEnterAdvance`/`useEscapeBack` handle the unfocused case — Enter only fires when nothing holds focus (a focused button already fires its own), Escape yields to any open popover (`[aria-expanded="true"]`) and to the prompt draft form before leaving the step.
- The theme is one external store (`useSyncExternalStore` in `lib/theme.ts`), not per-caller `useState` — four components read it, and a duplicated copy silently desyncs the ones that didn't toggle.
- **No em dashes in UI copy.** Recast with a period, comma, colon, or parentheses to fit the sentence. The standalone `—` is still the "no data" glyph in tiles and table cells (`pct`/`position` return it); that's a placeholder, not prose.
- Transient notices go through `useToast()` (`ToastProvider` sits at the app root) — bottom-center, self-clearing; use it for a refused action, not for form validation (that's the inline error line).
- Tables use the shared utilities in `src/app/components/table/table.tsx`: sort (`useSort`, nulls last), pagination (`usePagination`), resizable columns (`useColumnWidths` + `ColGroup`/`ColResizer` — a drag trades width with the neighbour so the total never changes; give every column a `fraction` for a stable default instead of letting the browser measure content), and `rowActivation()` for clickable rows (a bare `onClick` on a `<tr>` is mouse-only). Prompt detail opens in the shared `PromptPane` → `ResultPane` side panes (`src/app/components/panes/`).
